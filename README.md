# rhun extensions index

The extensions rhun lists under **Browse** on its Extensions page, and the only versions it
installs by itself as updates. Each extension has one file, `OWNER/NAME.ini`, pinning one
reviewed release:

```ini
# rhun-editor/extensions: rhun-editor/showcase.ini
category = tools
keywords = demo tour example
maintainer = vshvedov
featured = yes
# the reviewed release; a new version is a new pull request
tag = v0.1.2
commit = 93fff6aa75bf1e7063f912a17089ee58963bbc21
sha256.linux-x86_64 = …
sha256.macos-arm64 = …
sha256.windows-x64 = …
```

`category` is one of `languages formatters themes testing debugging tools packs other`;
`sha256.TARGET` is the digest of `NAME-TARGET.tar.gz` in that release (a target without one shows
"Not for this system"); `rhun = 0.19.0` names the oldest rhun the version works with. Title,
description, color, version, permissions and a pack's members come from the archive's own
`extension.ini`, which must name `OWNER/NAME` and the tag's version.

## Adding or updating an extension

Open a pull request that adds or changes `OWNER/NAME.ini`. Its checks (`.github/workflows/check.yml`):

- `go run ./tools/genindex -check`: every pinned digest against the release's `sha256sums.txt`,
  one archive downloaded and verified, its manifest's owner, name and version, the 64 MB limit,
  no links or devices in the archive;
- `rhun-ext-check` on the Linux build (the protocol's checker, from
  github.com/rhun-editor/extension-protocol);
- `gh attestation verify` of each archive against the pinned commit and the template's reusable
  release workflow;
- a review of the source between the previously pinned commit and the new one.

A person merges. A scheduled job (`bump.yml`) opens the pull request for a new release of a listed
extension; it still needs the review.

## How rhun reads it

On each merge to `main`, `publish.yml` runs `go run ./tools/genindex -out dist` and publishes
`dist/index.ini` and `dist/sha256sums.txt` as a new release; rhun fetches
`https://github.com/rhun-editor/extensions/releases/latest/download/index.ini`, checks it against
`sha256sums.txt`, and keeps it in `$XDG_STATE_HOME/rhun/extension-index.ini`. The format (INI that
rhun's own reader takes: whole-line comments, one-line values of at most 1000 bytes, at most
2000 entries and 1 MB):

```ini
# rhun extension index, generated by github.com/rhun-editor/extensions; do not edit
format = 1
generated = 2026-10-19T08:00:00Z

[rhun-editor/showcase]
title = Showcase
description = A tour of everything an extension can do in rhun: commands, edits, marks, prompts and more.
version = 0.1.2
tag = v0.1.2
commit = 93fff6a…
sha256.linux-x86_64 = …
sha256.macos-arm64 = …
sha256.windows-x64 = …
color = #2a9d8f
category = tools
keywords = demo tour example
needs = documents=write project=read terminal=yes
featured = yes
```

`needs` lists the manifest's `[needs]` as `KEY=VALUE` words (lists comma separated:
`run=gofmt,rustfmt`). rhun ignores keys it does not know; a `format` above 1 asks for a newer rhun.

`pending/` holds entries whose release is not published yet; the generator skips the folder.
